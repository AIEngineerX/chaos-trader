# Offline paper-agent walkthrough

This demonstrates a bounded trading agent, not just a report: the installed CLI evaluates evidence, waits, opens a simulated position, monitors it, closes it under existing policy, and records fills and realized results. **All external inputs are synthetic. Nothing here establishes live readiness or profitability.**

## Install and run

From this source checkout, with Python 3.11 or newer:

```sh
python -m venv .venv
. .venv/bin/activate
python -m pip install build
python -m build --wheel
python -m pip install --force-reinstall dist/chaos_trader-*.whl
python tools/paper_walkthrough.py --out ./paper-demo
```

On Windows activate `.venv\Scripts\Activate.ps1` instead. Use a new output directory for every run; the script refuses to overwrite one. Installation may need package-index access. The walkthrough itself disables network connections, strips inherited provider credentials and home settings, disables X, and uses only the existing HTTP fixture and indexed-wallet input fixture. It requires the checkout for fixtures, but verifies that product commands import the installed wheel, not the checkout or an editable installation. No server, provider subscription, wallet, schedule, or production book is used.

## What to inspect

Every numbered command writes `.stdout` and `.stderr`; `steps.json` lists commands and exit codes. `installation.txt` records the installed package location. `home/` contains isolated config, reports, and SQLite books. These artifacts include local paths: keep them private, rather than committing the output directory.

| Step | Real engine behavior | Expected evidence |
| --- | --- | --- |
| `01`–`02` | Onboard and inspect empty readiness | Missing/unsupported evidence is explicit, not greenwashed |
| `03`–`04` | Analyze a synthetic token and inspect strategy | Structured token/strategy output |
| `05` | Discover without sufficient source confirmation | `paper_wait` |
| `06`–`07` | Evaluate new synthetic indexed-wallet observations | `paper_enter`, one persisted open position |
| `07b`–`07c` | Refresh a sharply lower synthetic price/liquidity | `PAPER_CLOSED`, `liquidity_break` |
| `07d` | Inspect strategy against deteriorated inputs | `paper_avoid` (read-only inspection, not another entry) |
| `08` | Read actual paper accounting | Two fills, one closed position, zero open positions |
| `09`–`10` | Inspect outcomes and final readiness | Truthful missing or insufficient samples remain visible |

The script asserts wait/enter/avoid decisions, the closed position and exit reason, and fill/position totals. Each tick is a fresh CLI process. Only external observations are seeded: decisions, positions, fills, and exits are generated by the real engine. Demo-local analysis cooldown is zero; other shipped policy and caps remain intact. The script waits for the real ten-second market cache to expire before the exit tick rather than editing engine state.

## Recorded case

[Offline paper case](examples/offline-paper-case.json) is an allowlisted export from an executed walkthrough, not an invented response. It connects insufficient evidence and `paper_wait`, refreshed synthetic evidence and `paper_enter`, the persisted `liquidity_break` close, and actual paper accounting. It omits local paths, timestamps, token/wallet identifiers, raw provenance and operator details. Reproduce it with the commands above; compare the named decisions and accounting with steps `05`, `06`, `07c`, `08` and `09`. Run identifiers and timestamps will differ.

The case records a simulated loss, not a trading-performance claim. The separate 24-hour outcome cohort remains explicitly empty. Full-book rejections return and persist `paper_wait` with `budgets.max_open_positions reached`; they do not record an entry event or create a position/fill.

## Limits and next steps

- The indexed-wallet database is an existing test fixture, **not an ingestion validation**. No real wallet data is read.
- The short run records a paper loss in `paper-report`; `outcomes` measures a separate forward-window verdict cohort and correctly has no mature 24-hour samples. Do not confuse these reports or backdate samples to manufacture results.
- Bounded `--once` ticks prove evaluation and position management, not an always-running autonomous service. No schedule is enabled.
- Existing retry/reliability suites cover duplicate/restart/concurrent entry, trim and close, caps, and SQLite rollback; this walkthrough does not replace them or prove every lifecycle policy.
- Clean upgrades/restores, complete-tick readiness receipts, broader adverse evidence scenarios, and independent operational acceptance remain on the [roadmap](roadmap.md).
